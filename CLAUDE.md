# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

No build step or package manager. Open `index.html` directly in a browser, or serve with Python:

```
python -m http.server 8787 --directory "D:/Claude Apps/iridescent-prism"
```

Then visit `http://localhost:8787`. All data persists in `localStorage` — no backend.

## Styling: Tailwind via CDN

All styling must use **Tailwind CSS** utility classes. The project uses the Tailwind CDN (no build step):

```html
<script src="https://cdn.tailwindcss.com"></script>
```

Do not write custom CSS rules or add new entries to `styles.css` for new features. Use Tailwind utility classes directly in the HTML strings generated by `app.js`. When Tailwind's defaults aren't enough (e.g. a specific color not in the palette), use the `style` attribute for that one value rather than writing a new CSS class.

The existing `styles.css` is legacy — it predates this convention and will be migrated over time. Do not extend it.

## Design conventions

**Color scheme:** Dark backgrounds throughout. Use blue for all interactive elements — buttons, focus rings, active states, links, and hover highlights. The current palette maps to Tailwind's `blue-500` / `blue-600` / `blue-700` range for interactives and `gray-900` / `gray-800` / `gray-700` for surfaces.

**Task cards must show three fields at a glance, always:** assignee (avatar with initials), priority (colored dot + label), and due date (calendar icon + human-readable relative date). These three are non-negotiable — never render a task card without all three visible in the card footer, even if the field is empty (show a muted "—" placeholder rather than omitting the slot).

**Error messages:** Never expose raw error text, exception messages, or storage error codes to the user. Catch errors at the boundary and show a plain-language toast instead (e.g. "Couldn't save — please try again" rather than `QuotaExceededError: ...`).

## Architecture

Three files, no framework, no bundler:

- **`index.html`** — static shell only. All DOM structure is injected by `app.js` at runtime. The only meaningful static elements are `#sidebar`, `#main`, `#modal-overlay`, `#sidebar-backdrop`, and `#toast-container`.
- **`styles.css`** — legacy custom styles (being replaced by Tailwind). Do not add to it.
- **`app.js`** — all application logic. Single file, `'use strict'`, no modules.

CDN dependencies (loaded via `<script>` in `index.html`):
- **Tailwind CSS** — utility-first styling.
- **SortableJS 1.15.0** — cross-column drag-and-drop. Accessed as the global `Sortable`.
- **Inter + DM Mono** — Google Fonts.

## Data model

Two `localStorage` keys:

| Key | Shape |
|-----|-------|
| `ip_projects` | `Project[]` — full app state |
| `ip_active_project` | `string` — ID of selected project |

Tasks are embedded inside their parent project (`project.tasks[]`), not stored separately. All persistence goes through the `Store` object (`getProjects` / `saveProjects` / `getActiveId` / `setActiveId`). Wrap `Store` calls in try/catch and surface failures as user-friendly toasts.

```js
// Project
{ id, name, color, createdAt, tasks: [] }

// Task
{ id, title, description, assignee, dueDate, priority, column, order, createdAt }
// column: 'todo' | 'inprogress' | 'done'
// priority: 'Low' | 'Medium' | 'High' | 'Urgent'
```

## Rendering pattern

`app.js` has **no virtual DOM**. All rendering is full re-render via `innerHTML` on the relevant container:

- `renderSidebar()` — rewrites `#sidebar-projects`
- `renderBoard()` — rewrites `#board` (all three columns + cards), then calls `initSortable()`
- `renderTaskCard(task)` — returns an HTML string (called inside `renderBoard`). Must always include assignee, priority, and due date slots in the footer.
- `renderSplash(board)` — replaces board with the no-project state; sets `.board--splash` on `#board`

After drag-and-drop, **`renderBoard()` is NOT called** — SortableJS has already moved the DOM node. Only `updateTaskColumnAndOrder()` runs to persist the new order to `localStorage`.

After any modal save (create/edit/delete), both `renderSidebar()` and `renderBoard()` are called to sync counts and cards.

## Modals

A single `#modal-overlay` / `#modal-box` pair is reused for all modals. `openModal(html)` injects HTML string content and adds `.modal--open`. `closeModal()` removes `.modal--open` and clears `innerHTML` after the CSS transition (200ms). Event listeners are attached fresh on each `openModal` call — there is no persistent modal state.

Confirmation dialogs (delete project, delete task) open a second modal by calling `openModal` again, replacing the current content.

## SortableJS wiring

`initSortable()` runs after every `renderBoard()`. It destroys any existing Sortable instances on `.column__body` elements (`el._sortable`) before creating new ones. All column bodies share `group: 'kanban'` to enable cross-column drag. The `onStart` handler hides `.column__empty` placeholders; `onEnd` restores them based on remaining card count, updates column count badges, and calls `updateTaskColumnAndOrder()`.

## Responsive breakpoints

`≥1024px` — desktop grid, sidebar always visible. `640–1023px` — sidebar off-screen, board scrolls horizontally with `minmax(250px, 1fr)` columns. `<640px` — single-column stack, vertical scroll.
